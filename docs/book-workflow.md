# LLM Wiki Fork：沿用原版自动入库

默认流程：**书籍/报告 → 外部 MinerU（按需 DeepSeek 修复标题）→ 源文件包 → 原版资料入库队列 → 自动提取概念、关联并维护 Wiki**。短文章和笔记直接从同一个「资料」入口导入。

## 日常使用

1. 用已有 MinerU 技能处理书籍，需要修复标题层级时再用 mineru-deepseek-structure；导出 `source.md + manifest.json + images/` 源包。
2. 在「资料」点击导入，选择包内 `source.md`，或选择完整源包文件夹。一次导入的文件夹也可以同时包含源包、短文和笔记。短材料无需经过 MinerU。
3. 配置好入库模型后，导入会自动进入原版队列，分析材料、关联已有知识并生成或更新 Wiki。**无需先选择比较主题或再点击主题发现。**
4. 从原版 Wiki、搜索和对话入口阅读或提问。新增短材料继续从「资料」导入，已有 Wiki 会参与后续生成与合并。

阅读时，内部页面链接及来源卡片优先显示文档标题。原文定位显示为可点击编号，点击查看完整位置；一个连续区块范围使用一个编号，EPUB 内容项不等于页码。查看原始 Markdown 仍可看到完整路径和定位码，无需重新入库。

维护信息与逐节知识的详细出处、来源章节默认折叠，点击对应标题展开。同一文件的不同来源路径只显示一张卡片，同名的不同文件分别保留。逐节知识标题在阅读时与原有主题小节并列；这些展示处理不改写文件，检索和问答仍读取 Markdown 与原文证据。整理已有页的重复内容时应先留副本、核对独有条件与出处，再做相关问答回归，不能只保留屏幕上的短概述。人工修改过的受管知识块仍受原有停止覆盖保护。

## 图片描述与处理详情

图片提取、视觉描述、描述缓存和图片搜索沿用原版功能。在「设置 → 图片描述」开启「导入时生成图片描述」，可复用当前入库模型或原有独立视觉端点。Codex CLI 现通过图片附件传递真实像素，支持 PNG、JPEG、GIF；不支持的格式明确报错，不把省略图片后的文字回答当识图结果。附件最多4张、单张5MiB、合计12MiB；原版逐图描述每次发送1张。

已有资料可从「原始资料 → 处理详情」查看入库缓存、章节文本批次和图片描述数量，然后点击「继续提取到 Wiki」。继续使用原版队列；未变的文字复用入库结果，已有图片描述按图片哈希及输出语言复用，缺少描述的图片才调用模型。未启用、失败或取消的图片不会被当作全部处理成功；取消会停止本次CLI调用，已成功保存的缓存可用于下次继续。

文字已提炼、只需补图时，使用同一详情中的「仅补充图片」。该入口要求来源与入库缓存匹配、开启图片描述，复用原提图和描述缓存，只更新来源页的受管图片区；不重写主题页，也不重新核验文字覆盖。来源页并发变化、残缺的图片区标记或缓存不匹配时停止并保留现场。原有全文任务若因手工整理的知识页而失败，记录继续保留，不会被补图成功覆盖。

源包有明确相邻图题时，将原图号与描述一起供检索使用；图像和图题分别保留原文行号与已有定位。无法唯一对应时不猜关联，图题的未知页块也不借用图片页块。智能检索可按「图7-9」或「Figure 7-9」读取相关段落；图片描述仍是模型对原图的解释，应通过图卡回看原图。

处理详情按需读取现有记录，不修改原始资料。章节数字只统计当前来源、模型和规则匹配的文本检查点；图片数字只统计已提取图片及描述缓存。它们不是全书覆盖率，不能代替知识页、回答正确性和出处的分别核验。前言、附录与纯图像不计入逐节文本统计；复杂图表描述仍需对照原图抽查。

## 检索和原文问答

Wiki 是主题导航和综合层，不能替代完整原文。向量检索索引的是 Wiki 片段，没有写入 Wiki 的参数不会因为打开向量开关而自动出现。

- **传统检索**保留原有行为，适合先找已有主题页。
- **智能检索**在 CLI 模型下先解析来源指代并生成中英检索词，再执行一次有界的 Wiki＋原文检索；最多补读3个Wiki页面，每页按问题读取分散的相关段落、合计最多4000字符。当前问题中的明确来源或点选原文会限定检索范围；没有定义的“论文1/2”会先询问，切换来源后不把旧回答当证据。它不等同于 HTTP 模型的多步工具循环，仍可能缺少部分条件。
- **只读原文**在 CLI 模型下只把本轮原文摘录交给模型，不沿用历史回答或图片作为证据；没有摘录时直接说明不足。多轮问题应写清材料及对象。

原文检索会对各处命中排序，可返回同一本书的多个片段；每片段带附近标题、源文件行号及已有位置，短段会带入同小节相邻内容。一次最多10片段、每片段最多1500字符，不把整本书送给回答模型。行号属于解析后的正文，未知PDF页码保持未知。

当前原文检索仍是关键词匹配，CLI规划会为中文问题补充英文检索词。没有交代的来源别名会先澄清；关键参数分散在未召回章节时仍可能缺证据；看到相关结果不等于已经取得答案。需要核验数值、条件或工程要求时检查实际引文与原件。可重复的技术验收入口见 [检索对照验收](retrieval-validation.md)。

原版自动维护遵循项目 schema 和 purpose，不保证每次导入都额外生成一篇跨书专题文章。文件监听的自动入库遵循原版设置；显式导入仍走原版导入队列。没有可用入库模型时只保存来源，配置模型后可以从资料页入库。

源包的正文、图片和清单在写入前校验；只有全部准备好后才发布正文入口。相同源包重复导入复用身份，缓存和队列去重沿用原版；清单或图片变化产生不同源身份。不要直接编辑受校验源包，内容修改后重新导出并导入。普通 Markdown/TXT 的原版编辑、监听行为继续使用。

## 预处理书籍的章节边界

较长源包若已有明确的 Markdown 章标题，默认入库先按章处理，即使全文仍能装入模型上下文，也不再整本一次发送。长章优先按节，过长的节再按完整段落、表格、代码块或出处定位块拆分；每个子块携带章名、节名和章内序号，重叠仅取自同一章。原文件和来源身份保持不变。

这一约束读取 MinerU／标题修复流程已经提供的结构，不重新解析原始 PDF。正文句子不会仅因以“第几章”开头就被当成章标题。缺少明确章标题的材料继续沿用原有文档处理逻辑，不声称已经正确识别章节。

章节分析沿用可恢复的入库检查点，并校验分块方案与分析格式版本。模型必须返回独立的本块分析、更新后的全书摘要和结束标记；缺失时明确失败，不再把整段回复当成摘要累计。生成阶段接收章节分析与全书摘要，要求来源页包含逐章笔记和全书概览，再按原版机制关联其他书籍或短材料。实际内容覆盖和解释质量仍需验收，章节数齐全不等于知识点全部正确。

## 可选：证据研读

「证据研读」是按需使用的补充入口，用于显式分章、逐条引文核对、恢复检查点和定向比较。它不是日常入库的必经步骤。

需要这些额外核验时，在此导入预处理 Markdown/TXT，检查章节，再点击处理。完成后可选择至少两份材料，点击「查找比较主题」让模型拟出候选，再选择生成；也可自行输入具体比较问题。**这个补充入口需要手动触发，不称为后台自动发现。**

原版资料页的来源不会自动进入这个独立的核验证据池；只有需要逐条核验的材料才在此再导入。普通跨材料关联已经由原版默认流程处理。已有本地章节笔记、引文与比较记录保持原位置，不自动迁移或覆盖。

候选只使用已核对引文，至少关联两份材料；可以没有可靠候选。综合区分原著、报道与个人解读，不按篇幅判断可信度。相同来源版本和主题再次提交会复用已校验主题页、补齐索引，不重复调用模型。

## 外部导出器

Python 3 标准库即可运行，无需安装 Wiki 或调用模型：

```bash
python3 scripts/prepare-book-source.py \
  --markdown '/path/book.mineru/book.cleaned.md' \
  --structured-content '/path/book.mineru/local-result/structured_content.json' \
  --original '/path/book.pdf' \
  --output '/path/book.wiki-source'
```

`--structured-content` 与 `--original` 可省略。输出目录必须尚不存在，父目录必须已存在。原材料只登记文件名和 SHA-256，不复制入 Wiki；没有结构副产物时不声称有原件页码。

```text
book.wiki-source/
  source.md       全文、图片引用及明确匹配的原件位置
  manifest.json   输入/输出哈希、原材料标识、匹配数与警告
  images/         仅正文实际引用的图片
```

本机两个技能已经增加可选导出入口；运行方法见各自 `local-data/ADAPTATION.md`。它们复用同一个导出器，已有转换入口及默认策略保持不变。以后补充页标签、表格或其他定位数据，应优先扩展外部源包协议。

## 定位契约

- 结构映射仅接受 MinerU 4 `pages[].blocks`。按全部结构块做顺序对齐，只保留最佳对齐一致的精确匹配；标题仅允许 Markdown 层级标记不同。无匹配或有歧义就记录警告，不猜出处。
- PDF 使用从 1 开始的物理页和块编号，例如 `pdf-page:9/block:2`；EPUB 使用 `epub-spine:3/block:1`，spine 序号不是物理页。印刷页码未自动识别；明确为部分 PDF 且没有原始页映射时，不输出物理页定位。
- 每个匹配块前加入 `<!-- source-location: ... -->`，块末加入 `<!-- source-location: unknown -->`。初始状态为 unknown；后续未匹配内容不会继承前块出处。只有引文覆盖范围完全已映射时才附上原件块位置。
- 图片统一为内联 Markdown，保留 alt、移除 title、编码路径；仅接受 `images/` 内 PNG/JPEG/WebP/GIF。导出器拒绝远程图片、路径逃逸、图片软链接。正文不被改写；代码示例保持原样。
- Wiki 保留源包来源清单与图片并核对哈希。普通 Markdown 没有原件映射时，仍保留完整正文、章节、从 1 开始的行号及 UTF-16 半开字符范围。
- 「证据研读」中的模型引文必须在当前正文分段中存在，只允许空白排版差异；保存实际原文位置。无法找到的引文和未知证据编号会被拒绝。

引文校验证明文字存在和位置匹配，不能自动证明解释正确、论据充分或 OCR 结果无误。模型笔记与综合仍需结合原文阅读。

## 数据和恢复

新生成页面的源包引用还会核对本地身份是否存在；不存在的新引用被剔除并报告，既有历史来源保留。该检查不证明引用内容足以支持论断，也不自动清理历史页面。

默认入库沿用原版来源身份、队列、缓存和 Wiki 合并逻辑。源包只增加下列适配目录，正文保持原字节和相对图片引用；配图与清单不作为独立材料入库：

```text
raw/sources/<名称>--<清单SHA256>.wiki-source/source.md
raw/sources/<名称>--<清单SHA256>.wiki-source/manifest.json
raw/sources/<名称>--<清单SHA256>.wiki-source/images/
wiki/sources/                                原版来源摘要
wiki/                                        依据现有 schema 组织的 Wiki
```

以下为可选「证据研读」原有数据结构：

```text
raw/books/<book-id>/source.<ext>              导入源文件副本
raw/books/<book-id>/manifest.json             可选源包清单
raw/books/<book-id>/images/                   源文件引用图片
raw/books/<book-id>/<revision>/source.md      完整正文快照
raw/books/<book-id>/<revision>/<chapter>.md   章节正文
raw/books/<book-id>/<revision>/images/        章节引用图片
wiki/books/<book-id>/<revision>/              章节笔记和全书概览
wiki/synthesis/book-topic-<id>.md             跨书主题页
.llm-wiki/books/<book-id>.json                书籍清单与进度
.llm-wiki/books/<book-id>/<revision>/         分段检查点与证据
```

重复导入找到现有记录。源正文、图片或来源清单变化会产生新标识，不覆盖旧书；保存快照的哈希不一致则停止处理。原始 PDF/EPUB 继续由外部技能及用户保存，界面仅展示清单记录的原材料文件名。

可选证据研读的长短材料保存于兼容既有版本的 `raw/books/`，不会触发原版 `raw/sources/` 自动入库而重复调用模型。原版「只读来源」检索范围未扩展；证据快照通过「证据研读」和笔记链接阅读；默认导入来源仍在原版检索范围内。

手改笔记、概览或主题页不会被静默覆盖；首版不自动合并这些修改。同一进程内有按书籍和项目的写入锁，不支持两个应用进程同时写同一书库。主题发现与综合的证据超出上下文预算时明确报错，不截断；可在模型支持范围内增加应用上下文预算或减少所选材料。

## 模型配置

章节处理、概览、主题发现与综合均使用「Ingest 模型」路由。可在设置中独立保存 Ollama 配置而不启用它，不影响当前活跃 Provider。需要本地处理时，再将 Ingest 模型切换到该已配置 Provider。

内置 Ollama Provider 可连接使用者自行部署的本地服务；模型、上下文和超时根据机器与材料大小配置。Codex CLI 读取应用当前选择的模型，聊天与入库可分别配置。短文通过不代表完整长书与跨材料综合质量通过，使用前应针对自己的材料验证。

应用上下文的单位是字符，不是 tokens，也不会调整 Ollama 的 `num_ctx`。16K 字符可能不足以容纳整书证据；不要仅因 Ollama 报告大窗口就假定长上下文速度与质量已通过。向量模型 `qwen3-embedding:8b` 用于可选检索，不是本流程生成笔记和发现主题的前提。

## 验证与限制

```bash
python3 -m unittest discover -s scripts -p test_prepare_book_source.py
npm run test:mocks
npm run build
```

桌面构建沿用 Tauri，需 Rust、平台工具和 `protoc`。先运行 `npm --prefix mcp-server ci && npm run mcp:build`，再运行 `npm run tauri dev`。

`book-*.real-llm.test.ts` 默认跳过。显式设置 `RUN_BOOK_BASELINE=1` 或 `RUN_BOOK_WORKFLOW=1`，以及绝对路径 `BOOK_VALIDATION_ROOT`、`BOOK_VALIDATION_INPUT` 才调用已登录的 Codex CLI，使用账号现有用量。双书 INPUT 目录需由使用者提供 `validation-input.json`：包含两个 `books` 条目（各有 `file` 与 `expectedChapters`）和 `topic`；不内置材料名或主题。基线 INPUT 为单个 Markdown 文件，可另设 `BOOK_VALIDATION_CHAPTERS` 记录预期章数。测试用真实磁盘的 Node 适配器替代 Tauri IPC，桌面操作单独验证。

完整书籍、短材料与源包混合导入均有独立验证入口。验收应分别记录原文完整性、提炼覆盖、回答正确性、出处与原生交互；章节数或页面数不能替代内容验收。此次未新增后台调度，自动入库沿用原版监听与队列；没有任意书籍的 OCR、图表语义或知识覆盖保证。

实际材料、知识库、题集、回答、图片、日志及单次数据修订脚本均由使用者在源码仓库之外保存，不随源码或安装包发布。通用测试使用合成数据，真实验证只读取显式提供的外部路径；仓库中的忽略规则不能代替提交清单及安装包内容核对。

混合验证入口为 `RUN_BOOK_MIXED=1`，配合 `BOOK_VALIDATION_ROOT`、`BOOK_VALIDATION_EXISTING_ID` 和外部短记路径 `BOOK_VALIDATION_NOTE`。仅针对目录内已完成的书籍快照，添加使用者提供的短记，自动发现主题并生成一篇混合主题页；没有手工输入主题。


## 逐节知识与成页覆盖核验

有明确章标题的预处理书籍源包，在原版分析、生成及合并后，增加逐节文本证据记录。已有来源再次摄取时复用原版成功结果，只补该阶段，不重新生成整书摘要。短文章与没有明确章节的材料保留原流程。

每个文本块必须有知识去向或明确的背景理由。记录保留章节、原始行号与既有定位，`unknown` 不推断页码；方法记录保留条件、步骤、反馈、控制点和产出，案例、要求与展望分开。先核对原文覆盖，再检查主题页是否遗漏跨节适用条件或方法衔接。通过后把完整记录直接补入现有主题页；完整已有知识可引用其逐字正文复用，不要求每条记录单独成页。

检查点在 `.llm-wiki/section-knowledge/` 按来源身份、源文哈希、模型、schema及分段计划绑定，保留提炼/核验响应和写前副本。恢复时重新检查出处、页面正文及来源字段；原文或受管正文变化则报错保留现场。写入采用原生条件比较与原子替换，与应用编辑器保存共用写锁。原始材料不改；外部应用或另一实例同时编辑同一Wiki不在该进程锁的协调范围内。

这项核验针对预处理后的文本知识，不保证 OCR 原文正确，也不替代图像、复杂图表的视觉核验。前置内容和附录继续保留原版处理结果，当前逐节补全过程以显式正文章节为范围。模型核验通过仍须与真实问题抽查结果分开报告。

真实验证入口 `section-knowledge.real-llm.test.ts` 默认跳过。显式启用时要求既有 `.retrieval-validation-copy` 标记、隔离目录 `SECTION_COPY`、输出目录 `SECTION_OUTPUT`、源文件相对路径 `SECTION_SOURCE=raw/sources/<source>/source.md` 及从生产 Rust CLI 启动器导出的参数文件 `SECTION_CLI_ARGS`；请求 `gpt-6.1-terra` 并保留已验证的 Mem 隔离与安全参数。磁盘业务验证使用 Node 适配器；原生条件写入另以 Rust 并发/冲突测试和桌面预览核验，不能混称同一环境全流程。

## LLM Wiki 的 Codex CLI 与 Mem 隔离

LLM Wiki 启动的 Codex CLI 只负责本次模型请求。启动参数单独关闭标准 Nowledge Mem 插件、`nowledge-mem` MCP 和用户 `hooks.json` 中的受管 Mem 生命周期入口；不修改共享 Codex 配置、钩子文件或规则文件。日常 Codex 的 Mem 使用不受影响。

保留本地安全配置、PreToolUse、钩子信任及 execpolicy，并继续使用只读沙箱。旧的“隔离本地配置”选项会绕过安全配置，因此 Codex 调用在该选项开启时明确拒绝启动，关闭它后即可使用自动的 Mem 定向隔离。Claude Code 的设置不受此次改动影响。

如果 Mem 钩子使用无法拆分的组合命令、包装命令或配置格式异常，启动前报告错误，不悄悄退回会调用 Mem 的模式。此适配支持 `nowledge-mem@nowledge-community` / `nowledge-mem@local`、标准 `nowledge-mem` MCP 名称以及受管 Python 入口；自定义重命名集成需要另行适配。已有历史回答中的存档提示不会被改写，新调用的本地验证结果见项目交付预览。
